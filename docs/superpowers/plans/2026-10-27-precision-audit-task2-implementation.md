# Precision audit (task 2 of the publication recovery plan): implementation plan

Written 2026-10-27 by Claude, after Task 1 of [Codex's plan](2026-10-26-publication-recovery-after-results.md) was completed (D-096 to D-099). This file is MY plan for building Task 2 (the only new model experiment of that plan); the science and the budget are Codex's plan; open question Q29 asks the user whether to start (default: yes, in bounded steps). All new decisions go into new amendment files (`revision_R5_*.json` and later); the frozen transfer code, sample and original outputs are not changed.

## 1. Question and design (from the plan, restated)

Which transfer conclusions persist when the numerical implementation of the SUFFIX (layers above the SAE site, the final norm, the readout) changes while the cached prefix residuals, the stored weight values, the edits and the readout definition are fixed? Two execution modes: **bf16 suffix** (the existing runs: bf16 parameters, bf16 matmuls and attention, float32 residual stream and float32 readout) and **fp32 suffix** (the SAME bf16-valued parameters promoted exactly to float32, `cfg.dtype = float32`, everything in float32). 128 existing features x 4 contexts = 512 pairs, real and matched-swapped directions, states FP, INT16, INT4, the five cells of the study, plus repeated-batching controls.

## 2. Facts established by reading the code (so that the build is small)

- `phase1_transfer_run.process_items(items, suffixes, switches, ..., observer=...)` is the unit of work; `phase1_transfer_core.effect_many(..., observer)` calls `observer(tag, z, rows_list, targets)` with the raw float32 logits `z [1 + K, L, V]` (row 0 the unedited run) before they are reduced. **An observer can therefore capture the effect vectors of every cell of every item in each mode without changing the frozen runner**, and the cross-mode quantities are computed from the captured vectors (the stored chunk files hold only 5 x 5 Gram matrices within one run).
- The existing suffix is `model(resid, start_at_layer=13, stop_at_layer=n_layers)` of a TransformerLens `HookedTransformer` followed by `make_logits_fn` (float32 final norm, vocabulary-chunked float32 unembedding, soft cap). In TransformerLens (Ada, python 3.10 env) `RMSNorm` computes in float32 and returns `.to(cfg.dtype)`, attention uses parameter-dtype matmuls and `cfg.dtype` for the pattern, the block adds `resid_pre + attn_out` (a float32 residual stream plus bf16 outputs promotes to float32). So the fp32 mode is obtained by promoting the parameters of `blocks[13:]` and `ln_final` to float32 AND setting `cfg.dtype = float32` for the duration of the suffix call (the prefix `lower` and the SAE encode keep bf16).
- Weight states are made by `setup(label)` (restore the original state, RTN-quantize in bf16 storage). The plan requires promotion AFTER quantization without requantizing: the switch wrapper is **demote suffix to bf16 (exact, the values are bf16-representable) -> `setup(label)` -> promote suffix to fp32**; the pre-promotion bf16 values are hashed (sha256 of the bytes of every suffix parameter) per state, and the promoted copy is checked to equal them after `.to(bf16)`.
- Memory: Gemma-2-2B bf16 is about 5.2 GB; the upper 13 layers are about 1.0 B parameters (2.1 GB bf16, 4.1 GB fp32). In place: peak about 7.3 GB plus activations; use `max_rows` 256 (the main runs used 768) and the vocabulary-chunked readout of the existing code. RTX 2080 Ti 11 GB: expected to fit; the first chunk is a benchmark with a hard stop (plan: if the full scope exceeds the allowance report infeasible, never shrink the sample until it fits).

## 3. Steps (each: amendment/test first, mutation check, commit, handoff line)

1. **Selection (CPU; this step).** `scripts/g0/phase1_transfer_precision_select.py` + tests: from the committed core and the FP effect norms of the main tables (an FP-only quantity), the feature-level FP effect norm (median over the feature's 16 contexts of the real-direction FP effect norm), quartiles over the 404 features, 32 features per quartile by the lowest sha256 of `salt:feature id`, the first four contexts of each in the order of the frozen core. Writes `reports/intervention_transfer/precision_audit_freeze.json` (rule, salt, hashes of the inputs, the 128 features with quartile and contexts, selection sha256) BEFORE any GPU code; no quantized quantity, residual, desired sign or language enters.
2. **Amendment R5** (`revision_R5_precision_audit.json`): the protocol of the audit written before the code: modes, states, cells, controls, outputs, the comparison rules, the stop rules (memory, throughput), what would count as 'conclusions persist'.
3. **fp32-suffix machinery** `scripts/g0/phase1_transfer_precision.py` (new module): `promote_suffix(model, layer)`, `demote_suffix(model, layer)`, `suffix_hashes(model, layer)`, `dtype_probe(model)` (forward hooks at representative blocks asserting the expected dtypes of `ln1.hook_normalized`, `attn.hook_q`, `attn.hook_pattern`, `mlp.hook_post` in each mode), `mode_switches(setup, model, layer, mode)`, `fp32_suffix(...)`. Tests first with a tiny random-weight transformer built from the TransformerLens classes if the installed version allows it, otherwise a hand-written two-block reference module with the same dtype behaviour (exact, hand-computable: a float64 reference computed by hand must agree with the fp32 mode to float32 rounding and differ from the bf16 mode by more); the real-model gates on Ada: same-state/sham exactness (a zero edit is exactly zero in both modes), promotion round trip equal, FP/FP identical across two runs of the same batch.
4. **Cross-mode capture and analysis**: an observer that rebuilds the effect vector of every item/cell from the raw logits (same centering and mean over edited rows as `effect_many`) and keeps them on the host; per item the cross-mode 10 x 10 Gram of the cells of both modes (`tc.gram` with prefixed names); outputs: per state and mode the transfer norm, cosine and normalized error with the old fixed floor and a mode-specific floor, signed NLL change, the between-arithmetic change `|D_fp32[c] - D_bf16[c]|` relative to the between-weight-state change `|D[QQ] - D[FF]|` per mode, the INT16 reference, the repeated-batching controls (the same FP/FP cell in a different batch composition and order, both modes). No subtraction of squared noise norms; no rescaling of vectors.
5. **Instrument job on Ada** (first chunk only: memory, throughput, gates; the plan's stop rule), then the **full job** (one Slurm job, both modes, about 1 to 2 GPU hours expected), validated with the existing validator pattern, analysed ONCE; D-entry, README, report only if a claim changes.
6. **Decision** after the result by the plan's publication table: if apparent INT4 failures change substantially with arithmetic, that is an instrument result; if the INT4 drift persists, it is robust within the tested suffix setup (not a statement about deployed integer kernels or full-prefix precision).

## 4. Risks and how the build handles them

- `model.float()` alone is not proof of a float32 path: the dtype probes assert the internal tensors in both modes. If an attention kernel or a Gemma-2 specific op (sliding-window mask, attention soft cap) changes with the dtype, it is recorded and the comparison is labelled arithmetic-plus-kernel (plan).
- Quantization must not be redone in fp32: the wrapper order (demote, setup, promote) and the hash check guard it.
- The 2080 Ti has no native bf16: bf16 execution there is emulated/upcast inside the kernels, so the 'bf16 suffix' of the existing runs may already be partly float32 internally; the dtype probe records what actually happens (this is itself a finding about the instrument).
- Throughput: fp32 matmuls on Turing are fast enough (no tensor-core bf16 path), expected comparable to bf16; measured on the first chunk.
- Selection leakage: the selection script reads only FP columns and is tested to ignore quantized columns; the freeze file is committed before any run.
- Scope: this is an instrument-validation sample (512 pairs), not new language-generalization evidence and not a replacement of the main population.
