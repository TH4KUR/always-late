# wandb schema v2, extension for the GPTQ extension and the survival-versus-effect analyses (design; written 2026-10-29 00:32 IST BEFORE any code)

Context: plan Task 13 of [`2026-10-27-gptq-matched-comparison.md`](../docs/superpowers/plans/2026-10-27-gptq-matched-comparison.md) lists "small result files and logs to the private HF dataset and wandb in the fixed schema". The Hugging Face part is done ([`artifacts.md`](artifacts.md)). The schema v2 post-hoc upload of the finished results ([`wandb_schema_v2.md`](wandb_schema_v2.md), D-091, user's "option A" of 2026-10-26) has runs only for the OLD result families. **Open question Q32** asked whether to extend it; its default (a) is to build a compact set while time remains before 31 October, which is this design. The user can say skip at any time.

## 1. Principle and what does not change

Same as v2: **post hoc upload of FINISHED results, every number read from a committed file, nothing retyped**; project `anlp-project`, entity `karma-skz-`; deterministic run ids `v2-<slug>` (`resume="allow"`), tags `schema-v2`, `post-hoc-upload`, the status tag, the slug and the group, `job_type = analysis-upload`; config keys exactly those of v2 section 3; summary keys `headline/<name>` plus `n_tables`, `n_images`, `n_files`; no weights, no item-level `.pt` files, no keys, no Llama raw files; the older runs and the 19 + 18 existing runs are never touched. The existing builder and uploader (`scripts/g0/wandb_upload_v2.py`, 66 tests, 67 mutants) stay **unchanged**: they already accept any list of families (`build_all(root, families, ...)`) and any payload (`upload(payload, root, wandb, ...)`).

## 2. What is new

1. **A second family list** `FAMILIES_EXT` in a new module `scripts/g0/gptq_ext/wandb_ext.py` (nine runs, below) and a thin command line (`build`, `upload`, `verify`) that calls the v2 functions with it. A test asserts that the new slugs never collide with the v2 slugs or the old run names and that every family passes the v2 builder.
2. **A derived headline file**, because the v2 builder reads headline values only from committed JSON and most extension results are CSV or per-arm JSON: `reports/gptq_extension/wandb_headlines.json`, written by `scripts/g0/gptq_ext/wandb_headlines.py` from the committed result files (per-arm values computed with the same arithmetic as the committed generators: `make_project_results_tables.py`, `compare_stage1.py`, `compare_transfer.py`), committed, and **regenerated by a test that must reproduce it byte for byte** (so no number is typed by hand). Headline metric paths then point into it: `M("headline/<name>", "reports/gptq_extension/wandb_headlines.json", "<slug>", "<name>")`. The two survival-effect runs read the result JSON of D-113 and D-114 directly.
3. **Arms in names, not in separate runs.** One run per study (compact); the three arms of a quantity are three headline keys with the suffixes `_legacy`, `_matched`, `_gptq` (for example `headline/survival_mean_INT4_gptq`), the same base name in every run where the quantity occurs; the committed three-arm tables go in as `wandb.Table`s.
4. **Config.** `model`, `sae`, `layer` as the Gemma runs of v2 (Llama run: its own); `quantizer` = "three arms, weights only, simulated by dequantized weights: legacy RTN (shared Q/K/V scale), matched RTN (per-output-channel grid), GPTQ (error compensation, 221,184 Wikipedia calibration tokens)"; `states` the precisions covered; `slurm_jobs` from the ledger job table; `code_ref` the snapshot commit (`88cfa491...`; Llama `c0ccaf0...`); `freeze_file` `reports/gptq_extension/freeze.json` (the survival-effect runs: their own freeze or addendum); `status` all **exploratory**; `limits` in words from the decision entries.

## 4. Tests and checks (before any upload)

- **Headline file:** regenerated by a test byte for byte; one pinned value per family from the decision entries (for example run 1: INT4 survival 12.7 / 18.7 / 30.5 %, loss increase 0.590 / 0.385 / 0.130; run 4: median INT4 retention 1.54 / 1.36 / 1.22; run 6: INT4 W1 median 0.839 / 0.875 / 0.923; run 7: INT4 net harm at x0.088 0.323 / 0.281 / 0.187 relative to FP 0.169) and each pinned value cross-checked against the number in `RESULTS.md` / the D-entry text; mutation battery on the generator (arm swaps, wrong state, wrong column).
- **Families:** v2's own builder runs on the extension list (paths exist, hashes, caps, scalar metrics only); unique slugs; every decision id exists in `decisions_and_anomalies.md`; `limits` non-empty; no path under `third_party/`, no `.pt`.
- **Dry run:** `build --dry-run` prints the payload summary; the build refuses files that differ from the committed version (the v2 dirty check).
- **Upload:** built locally, the payload and the file archive copied to Ada, `upload` run there as for the v2 runs (credentials of that environment; none printed or copied), then `verify` reads each run back through the API and compares the summary values, the config `files_sha256` and the number of tables with the payload (a test with a fake API covers `verify`).

## 5. Not in this extension

wandb runs for the old families are untouched; no new figures; no raw files; no deletion of anything on wandb. If a verification fails, the run is re-uploaded by its deterministic id (`resume="allow"`), never deleted.
