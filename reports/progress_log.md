**Quantization-survival demo: real bug found and fixed on first GPU
attempt.** `src/rtn_quant.py`'s `quantized_model` context manager cloned
all 182 target weight tensors onto the GPU before quantizing, to allow
restoring the originals afterward -- this nearly doubles resident weight
memory (Linear projections are ~90% of the model's parameters) and hit
`torch.OutOfMemoryError` (7.62GiB usable, model+clones needed ~10GB). A
second, independent bug then masked the real error: the `finally` restore
loop unconditionally indexed `saved[name]` for every target, but `saved`
only had entries for layers processed before the OOM, raising `KeyError`
on exit instead of surfacing the actual `OutOfMemoryError`. Fixed both:
stage the original weights on CPU instead of GPU (small transfer cost,
paid once per bit-width, not per token), and only restore names actually
present in `saved`.

### Findings (details and line references in `issues.md`)
- Core machinery looks correct; the paper's numerical tables trace back to the JSON (Fisher p-values, Spearman rho reproduce).
- Headline interpretation is unsupported: RQ1 is at ceiling (INT7 99.87 vs 99.96%, INT6 97.01 vs 97.35%); INT5/INT4 flip sign; a tier gap exists (INT6 High 99.05 / Mid 99.3 / Low 94.4%; language-level permutation p ~ 0.0003-0.003, computed from `by_language`), contradicting the paper's "null, so upstream" conclusion.
- Pre-registered safeguards/tests not implemented (bootstrap peak-language stability, language-level permutation test with script covariate, mixed model, TOST). The null cutoff 3.000 is not a calibrated null (6 high-resource languages, 500 tokens, 20 permutations). Holm implementation lacks the stop rule (latent).
- Content is not matched across languages: at a 20k-token budget English uses 774/997 dev sentences, Khmer 127, Lao 165. BOS is counted as an ordinary token (0.78% of tokens); 0-32% of chunks change tokenization on decode/re-encode.
- Stale or synthetic artifacts remain (`analyze_selectivity.py` figures from `np.random`, `selectivity_summary_table.csv`, README numbers from the superseded 1,500-token run).

### Gate G0 (Duan 2026): what we learned
- Our pipeline was an **independent re-implementation**, not Duan's code, and was never run on their data. Earlier wording ("matching Duan's protocol exactly", "reproduced Duan's results") overstated it.
- Downloaded their full artifact (zip sha256 `447f25e5...2478`) to `../duan-sae-feature-survival/` (outside the repo; read only, never executed). Their quantizer is the same recipe and the same 182 modules (their `n_quantized_params` = 2,024,275,968 = 26 x per-layer count). Differences: no BOS token, TransformerLens bf16 instead of HF, 256- vs 128-token windows, fp32 vs bf16 SAE, Q/K/V scale grouping, WikiText vs FLORES.
- Their baseline WikiText-2 perplexity is 458.5 (chunked, no BOS) vs 46.4 in their own sliding-window run (BOS, 2,048 tokens). Perplexity vs bits is non-monotone in both (INT7 -5.6% chunked, -6.5% sliding). Their sliding-window table re-uses the chunked survival numbers; no feature measurement exists under BOS/sliding evaluation. Their INT8 median r is 0.971 vs ours 0.9999.
- Their released per-feature file reproduces their INT6 headline row exactly (51.302 / 48.698 / 0.0). In that data, survival tracks activation magnitude (Spearman 0.78) and not firing rate (-0.085): our firing-rate-quintile matching does not control the main driver.
- Correction to the earlier entry of this review: the claim that "healthy Gemma gives low-teens perplexity" was my recollection, not a measurement, and their own BOS run gives 46.4. Our own WikiText-2 perplexity has never been measured.

### Were there implementation errors?
**Verified correct (by tests and runs against their code, 2026-10-16):** the JumpReLU encoder is identical to the `sae_lens` SAE their script uses (active sets identical on 4,096 positions, max value difference 0.0); the quantize-then-restore path leaves the model bit-identical; with a BOS token, our pipeline run on their tokens agrees with their own code with a BOS token (HF `O_keep` vs `T_keep`: -0.04 pp at INT7, +0.83 pp at INT6; their TransformerLens run R2 vs HF `T_mask`: +0.01 / +0.06 pp). **We found no computational bug that makes the old pipeline's numbers wrong for the regime it ran in** (BOS present, WikiText, INT8-INT6).

**Real flaws of the old codebase, independent of the disagreement** (`issues.md`): BOS counted as an ordinary token in every statistic (D1: 0.78% of tokens, enters the "universal" pool); decode-then-re-encode changed the tokens in 0-32% of chunks and chunks start mid-sentence (D2); everything bf16 with no noise-floor control (D3); the reported run not reproducible from the repo as documented (D4); synthetic figures and hard-coded fallbacks (D5); panel not content-matched (C1); the "null cutoff" not a calibrated null (C3); feature-level tests on clustered features (C4); controls matched on firing rate only while activation magnitude is the main predictor of survival (C6); Holm implementation without a stop rule (C5); Phase-1 never validated against a reference.

### Why the results conflicted (ours 98.28 / 94.31 at INT7 / INT6 vs theirs 81.26 / 51.30)

| factor | effect on INT7 / INT6 survival |
|---|---|
| **BOS token in the windows** (their pipeline, none vs one masked BOS) | **+18.55 / +46.17 pp** (perplexity 457 -> 16; INT7 stops "improving" perplexity) |
| their q/k/v scale sharing, **without BOS only** | +7.74 / +3.57 pp when replaced by per-row scales; with BOS: +/-0.83 pp |
| sdpa attention without soft-capping; bf16 SAE | +0.03 / -0.08 and +0.05 / +0.02 pp (none) |
| small demo (2,048 tokens of WikiText-test) vs 500k | our pipeline with BOS on their tokens is +1.56 / +4.88 pp above the demo (not isolated) |
The root cause is a **regime difference, not a bug on either side**: they feed 256-token windows with no BOS (a regime in which the model itself is degraded: baseline perplexity 457 against 16 with BOS, in both stacks), we always had a BOS. Their 81% / 51% are reproducible (their code on Ada, within 0.15 pp) but are a property of the no-BOS regime. - **Mechanics: sound.** An HF pipeline of this kind reproduces their TransformerLens results in both regimes (anchor `T`; `O_keep` vs `T_keep` vs R2). So the idea of measuring SAE feature survival with our own light stack was not wrong.

(2) Its distinctive parts (FLORES panel, selectivity score, tier tests) carry unresolved design flaws (C1, C3, C4, C6, D1, D2). - **What is worth exploring now (recommendation, not a decision):** (a) the regime question, because survival numbers in this literature depend on BOS handling by 18-46 pp at INT7/INT6 (a verified finding in two stacks); (b) a BOS-regime language-selective analysis at INT6-INT4 with matched content, language-level statistics and activation-magnitude-matched controls. **Training and special tokens: what the sources establish.** Gemma-2-2B was trained on ordinary text, not "BOS/EOS tokens only": the [Gemma 2 technical report, section 3.1](https://storage.googleapis.com/deepmind-media/gemma/gemma-2-report.pdf) describes two trillion training tokens from sources including web documents, code and science articles. BOS and EOS are special sequence delimiters. In an [official Gemma discussion](https://huggingface.co/google/gemma-2b/discussions/41), Google researcher Surya Bhupatiraju confirmed on 10 April 2024 that their pretraining batches use BOS and EOS delimiters; the raw comment was checked through the [public discussion API](https://huggingface.co/api/models/google/gemma-2b/discussions/41), because the rendered HTML hides the angle-bracketed token names. These sources support BOS-prefixed evaluation, but do not establish that every Gemma-2 training window began with BOS or that our evaluation must append EOS.

**The general BOS dependence is known, not a new discovery.** [Owen et al. (2025), *A Refined Analysis of Massive Activations in LLMs*, section 4.2](https://arxiv.org/pdf/2503.22329), directly studied Gemma-2-2B and Gemma-2-9B, reporting changed activation patterns and worse perplexity when BOS is omitted. [Barbero et al. (2025), *Why do LLMs attend to the first token?*, sections 3.2 and 5](https://arxiv.org/html/2504.02732v1), provide a related explanation: attention sinks can help a model limit unwanted mixing between token representations; models trained to rely on an initial BOS can lose that mechanism when BOS is removed. Their Gemma analysis concerns Gemma 7B, and their controlled training experiments are not a direct mechanistic diagnosis of our Gemma-2-2B FLORES runs. Thus, our observed direction is consistent with prior work, while the exact FLORES magnitude and its interaction with quantization have not been mechanistically isolated. We do not claim novelty or open a duplicate research question for the general effect; the existing Q5 retains the optional longer-window diagnostic.

**What this establishes about Duan's experiment.** Their [released token-building code](../third_party/duan2026/pristine/scripts/03_gemma_phase3_streaming_sweep.py) disables special-token insertion and supplies token tensors without BOS. Our controlled audit shows that adding BOS substantially changes both baseline prediction quality and the reported survival percentages. This supports a specific methodological criticism: their Gemma survival estimates depend strongly on an input convention that degrades the unquantized model, so those estimates cannot be assumed to describe compression during ordinary BOS-prefixed use. [Duan (2026), section 3.5 and Appendix D](https://arxiv.org/html/2606.03002v2), acknowledges the unusual chunked perplexity and checks a sliding-window protocol, but does not discuss BOS; that additional experiment evaluates perplexity rather than remeasuring SAE survival under the changed protocol. It does not resolve the BOS dependence of the survival result. This criticism does not establish that every claim in the paper is false, or that all measured feature changes are numerical artifacts.

**Decision (Q1 option a; confirms D-001, recorded as D-027).** Use the tested `mask` regime as the primary multilingual analysis: prepend one BOS to each input sentence and exclude BOS and padding positions from feature statistics. The distinction between retaining special tokens in model input and excluding their activations from SAE measurements is consistent with [Lieberum et al. (2024), *Gemma Scope*, sections 3.1 and 4](https://arxiv.org/html/2408.05147v2), which exclude BOS, EOS and padding activations from SAE training and evaluation metrics. **2026-10-23 07:57 IST, functional study (F5): the answer to "does a feature perform the same function before and after quantization?" The language-association status of D-035 carries no information about function at equal activity. Of the three pre-proposed statements two are met and one cannot be evaluated (at INT4 almost no feature stays inside the noise), so the overall verdict is undetermined; the first is met only because at INT6 almost every feature is inside the noise. **2026-10-23 19:20 IST, association study (A2): losing the language association is mostly a matter of how borderline a feature already was.** For the 6,663 language-selective features that were established in full precision, the gap between the strongest language's firing rate and the runner-up's in full precision predicts which features lose their language association after quantization: within a language, ranking features by that gap separates lost from kept ones with a score of 0.90 at 6 bits, 0.81 at 5 bits and 0.75 at 4 bits (0.5 would be chance). In the most borderline fifth of a language 21 % lose the association at 6 bits (33 % at 5, 54 % at 4); in the least borderline fifth 0.1 % (0.8 %, 7 %). Rounding-only noise already flips 3.8 % of the most borderline fifth and none of the rest. Activity scale and target share add little once the gap is known. Together with the functional results this says the association status is a threshold statistic, not evidence that a feature lost its function. Exploratory; the hypotheses were written before the numbers. [Decision D-066](decisions_and_anomalies.md), [report](association_retention/results/within-language/report.md).
